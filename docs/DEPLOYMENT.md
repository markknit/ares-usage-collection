# Deployment

## 1. Public phone-setup portal

Deploy the contents of `public/` under a stable HTTPS path such as:

```text
https://areseducation.org/phone-setup/
```

The teacher-facing entry point is `public/index.html`; installation instructions are in `public/setup.html`.

The setup page expects the Android package at:

```text
public/assets/downloads/ares-sync.apk
```

Do not publish credentials, enrollment codes, private school data, live rclone configuration, or signing keys in `public/`.

## 2. Production APK

The current `0.8.0-rc6` APK is a validated CI debug build used for field testing. Do not make a debug-signed APK the permanent production package.

For production distribution:

1. Build a release APK with the approved ARES signing key.
2. Keep the keystore, passwords, and signing secrets outside the repository.
3. Record the release version, versionCode, commit SHA, and SHA-256 hash.
4. Test the exact signed APK on a clean Android phone.
5. Copy the approved file to `public/assets/downloads/ares-sync.apk`.
6. Verify the published file hash matches the approved release hash.
7. Keep the previous approved APK available privately for rollback.

Do not silently replace the public APK. Treat every replacement as a release event and rerun the release checklist.

## 3. Android sideload behavior

During direct ARES distribution, Android may require the user to allow installation from the browser or Files app used to open the APK. Some phones may also display a Play Protect warning.

The teacher setup page explains this flow. Do not instruct users to disable Play Protect globally. If a phone does not present a safe way to install the approved ARES APK, stop and provide technician assistance.

A Play Store, managed-device, or enterprise distribution channel could reduce this friction later, but is not required for the current rollout.

## 4. Enrollment

The phone requires normal internet access for first-time enrollment.

The teacher searches for the school, selects the canonical school, and enters the one-time school-specific enrollment code generated by ARES staff. The central service returns the device ID and credential, which are stored privately by ARES Sync.

Never publish the enrollment admin key, enrollment secret, device credentials, or central school registry.

## 5. Local ARES server

Deploy the school-side usage collection package with:

```bash
sudo bash local-server/install_usage_collection.sh --school-code ARES-S00XX
```

The installer deploys the approved usage-export wrapper, PHP endpoints, collection schedule, configuration, upload directory, and scoped sudoers entry.

After installation, validate the existing report builder and the state-aware scheduled endpoint as documented in `docs/TECHNICIAN_SERVER_INSTALL.md`.

## 6. Central HTTPS collection

ARES Sync uploads pending reports directly to the central HTTPS upload service after normal validated internet becomes available. Phone-side Round Sync, Automate, MacroDroid, rclone, Google Drive configuration, and public Downloads-folder handling are not part of the production architecture.

The central HTTPS service writes accepted uploads to its protected incoming directory and authenticates each enrolled device.

## 7. Central processing

Run `central-monitoring/process_incoming.py` against the protected local incoming directory. Example:

```bash
python3 central-monitoring/process_incoming.py \
  --incoming /path/to/monitor_upload/incoming \
  --archive /path/to/ares-archive \
  --state /path/to/processed.json \
  --report-command '/path/to/report-command'
```

The processor validates filenames and CSV structure, suppresses exact SHA-256 duplicates, quarantines invalid files, archives accepted uploads, and optionally runs the reporting command once after newly accepted files.

Live central scheduling/cron or systemd wiring must be validated separately before production go-live.

## 8. Release and rollback

Before production deployment:

- complete `docs/RELEASE_CHECKLIST.md`;
- record the approved APK hash and commit;
- verify the setup portal downloads the exact approved APK;
- run one clean enrollment/install test;
- confirm the production school schedule is installed;
- confirm central processing does not ingest known controlled acceptance-test data unintentionally;
- retain the previous approved APK and deployment package for rollback.
